# SRanger re-run (October 2026)

> **Behaviour stage superseded (2026-10-19) — see `../auv/experiment/BEHAVIOUR_RERUN_2026-10-19.md`.** This record is the pre-fix baseline; the pre-fix artefacts are under `output/rerun/.../run_*/behaviour_v1/`.

**Why.** The archived SRanger behaviour model (`output/runs/sranger_deepseek_demo`)
deadlocks: its terminal `Final` is an ordinary state with no outgoing transition
(`fdr_results.json`, key `sranger_deepseek_demo`). This re-run exercises the full
pipeline on SRanger after (a) the terminal-state rule was added to the behaviour
prompts and a pre-FDR structure check to the gate (ported from FORGE's F16 rule,
`MALCOMp/stm_structure.py`), and (b) the upstream-isolation fix (`d9c740a`).

**Protocol.** 5 runs, DeepSeek-V4, cooperating configuration, all four stages,
every gate live (EOL execution, FDR), strict mode, repair budget 5.
`scripts/rerun_sranger.sh 5`; summary by `scripts/summarise_sranger.py`.

## What the attempt logs show

1. **The first generated behaviour model always fails the CSP generator -- and the
   cause is the assembler, not the generated model.** (Corrected 2026-10-19; the
   first version of this record blamed the LLM.) Every first attempt *declares* its
   variables and constants inside the `stm` (`var linVel : real`, `const moveVel :
   real = 1.0`, ...). The vendored FORGE template rebuilds the machine body from
   nodes and transitions and sources state variables from an interface FORGE's own
   pipeline supplies, plus guard-mining; declarations made inside the stm and used
   only in state entry actions were dropped, and declared constant values were
   replaced by the template default `= 1` (`turnDuration = 2.0` became `1`). The
   generator then reported "Couldn't resolve reference". The repair agent "fixed"
   this by re-adding the declarations to the assembled file -- i.e. it repaired the
   assembler's damage. Fixed in `RoboChartAssembler.promoteMachineDeclarations`
   (+ one recorded template adaptation): re-assembling all five first-attempt models
   with the fix, the CSP generator accepts 5/5 (was 0/5). The AUV models, whose
   variables all appear in guards, assembled identically before and after.

2. **Run 4 repeats the Table 1 failure pattern.** After repair 1 the model passed FDR,
   but `trace_resolved` still failed (the trace agent's output did not resolve), so in
   strict mode the loop continued; repairs 3-5 introduced a duplicate declaration and
   the model never recovered. A verified model was destroyed by repair driven by a
   traceability failure. Same mechanism as `TABLE1_V2.md`, reading 3.

3. **The concept stage fails `trace_resolved` in every run and repair cannot fix it.**
   SRanger's architectural requirements (SR-ARCH1/2) describe the controller's
   composition; the concept agent correctly emits a `Concept` (e.g. `Controller`) with
   no `Instance`, and the locator finds no instance to resolve. This is the
   instance-vs-type-name distinction already documented for the AUV
   (`malcom.evaluation/metrics/traceability`): a type-level link is not a defect in the
   concept model, and five repair rounds change nothing. Concept output is otherwise
   schema-valid and every downstream stage consumed it.

## Implications

- **For the paper's second-platform claim.** With the terminal-state rule in place, the
  pipeline produces an FDR-verified SRanger behaviour model in 4 of 5 runs after one
  repair. The honest statement is "generated models verified in four of five runs; the
  fifth was verified after one repair and then broken by further repair", not
  "proven deadlock-free".
- **For the pipeline.** Three changes follow directly from the logs, all made on
  2026-10-19 and all outside the behaviour prompt: (i) `trace_resolved` no longer
  drives repair of the artefact and the loop stops when structural checks pass
  (`VerificationResult.repairable_failures`); with this, runs 4 (SRanger) and
  002/004/010 (Table 1) would have ended verified; (ii) the structure check now
  rejects a state and a pseudostate sharing a name, the exact defect those four
  repairs introduced; (iii) the assembler keeps the stm's own declarations and
  values (above). The behaviour stage is to be re-run under these fixes
  (`scripts/rerun_behaviour_stage.sh`); this record is the pre-fix baseline.
